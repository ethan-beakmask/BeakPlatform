第 1 篇　封包路徑：從 Internet 到被保護網站

一個 HTTP 請求從攻擊者的瀏覽器出發，到被保護網站回應為止，依序經過哪些站、每一站看到的「來源 IP」是誰、哪一站有能力把它擋下來。

一、對外公開時的完整路徑（經 Cloudflare Tunnel）

圖 1-1　經 Cloudflare Tunnel 的請求路徑，以及每一站認得的客戶端 IP、能不能擋、Suricata 看不看得到、留下什麼紀錄。

圖中的攻擊者位址 203.0.113.42 不是真實 IP：203.0.113.0/24 是 RFC 5737 保留給文件範例用的 TEST-NET-3，不會出現在 Internet 路由上。安裝包的 --test-event 送的測試事件也用這個位址，而平台的保護清單刻意不把它列為受保護網段，正是為了讓端對端驗證能拿它當「公網攻擊者」走完整圈。

Cloudflare 是建議的對外方式，本架構完整支援。安裝包內含 cloudflared 服務（compose profile tunnel）與 cf_tunnel.py（用 Cloudflare API 自動建 tunnel、ingress 與 DNS），安裝時給 --cf-api-token 與 --cf-hostname 就完成；沒有網域時也可以在 Zero Trust 後台手動建 tunnel。不用 Cloudflare 也能運作，第二節的內網直打路徑就是，差別只在對外入口與攻擊者 IP 的歸因來源。

逐站說明

站位置發生什麼事
1攻擊者對外 hostname 的 DNS 記錄是 CNAME 到 <tunnel id>.cfargotunnel.com 且由 Cloudflare 代理，解析到的是 Cloudflare 的 anycast IP。攻擊者從頭到尾拿不到主機 B 的 IP，主機 B 也沒有對 Internet 開任何入站埠。
2Cloudflare edge終結 TLS，把真實來源寫進 CF-Connecting-IP、國別寫進 Cf-Ipcountry，並依帳戶方案套用 DDoS 與受管 WAF 規則（這部分不屬本安裝包）。然後把明文 HTTP 塞進 tunnel。
3cloudflared 容器tunnel 是 cloudflared 從主機 B 主動連出去的長連線（QUIC 或 HTTP/2），Cloudflare 把請求沿這條既有連線送回來。cloudflared 依 ingress 規則轉發：hostname 與路徑前綴符合被保護網站的送 http://waf-nginx:8080，其餘路徑送 http://waf-welcome:8080（歡迎頁，有自己獨立的 WAF）。這一跳走 docker 內部網段，不經過實體網卡。
4waf-nginx 容器nginx 收到明文 HTTP，交給 ModSecurity 依 OWASP CRS 在四個階段檢查（請求標頭、請求本文、回應標頭、回應本文）。累計異常分數達 5 即回 403，不再往後送；沒達門檻就 proxy_pass 到 --backend 指定的網站，並帶上 X-Real-IP、X-Forwarded-For、X-Forwarded-Proto，原始標頭（含 CF-Connecting-IP）也一併轉過去。
nginx 的 real_ip 模組刻意設成永遠不會匹配的值，所以 ModSecurity 記下的 client_ip 是直連它的對象（cloudflared 的固定 IP 172.18.0.250），這是後面 Vector 判斷「標頭可不可信」的依據，見第 5 篇。
5主機 B 實體網卡容器對外連線經 docker 的 MASQUERADE，封包來源變成主機 B 自己的 IP，從實體網卡送往內網的後端。這是 Suricata 唯一看得到這次請求的位置。Suricata 設定了 XFF 覆寫（mode: overwrite、header: CF-Connecting-IP），告警裡的 src_ip 會被換成標頭裡的真實攻擊者，而不是主機 B。
6被保護網站看到的 TCP 來源是主機 B；要知道真實訪客得讀 X-Forwarded-For 或 CF-Connecting-IP。回應原路回去，經過 WAF 的第 3、4 階段（回應檢查：異常分數門檻 4，抓 SQL 錯誤訊息、原始碼外洩之類），再經 tunnel 回到 Cloudflare、回到攻擊者。
被 WAF 擋下的請求，Suricata 看不到。403 在第 4 站就回頭了，永遠不會走到第 5 站的實體網卡。所以「同一次 SQL injection 同時有 WAF 事件與 Suricata 事件」只在 WAF 放行時才可能發生。反過來，Suricata 對第 5 站看到的是「WAF 已經放行的請求」，它抓到的東西通常是 CRS 沒涵蓋的型態（掃描器指紋、惡意 User-Agent、特定 CVE 特徵）或後端回應中的異常。

二、內網直打的路徑（安裝後驗證用）

沒有網域或還沒接 Cloudflare 時，從內網直接打 http://<主機 B>:8080 也會經過 WAF。路徑短很多，但多了兩件事：nftables 的來源管制，以及 Suricata 會看到兩次。

圖 1-2　內網直打 8080 的路徑。nftables 在這裡是第一道門，Suricata 會在請求進來與轉出時各看到一次。

三、nftables 在路徑上的實際位置

nftables 是主機 B 最外層，但它有兩個 hook，管的對象不同。這件事決定了「封鎖清單到底擋得住什麼」，第 5 篇會再回來談。

nftables chainhook管到的流量規則內容
inputinput，priority -100目的地是主機 B 本機程序的封包：SSH、od-bridge 8500、任何 host network 的服務來源在 allowlist（平台主機、ADMIN_IPS）一律 accept；來源在 blocklist / blocklist6 一律 drop。封鎖決策落地的就是這兩個 set
ingest_guard_forwardforward，priority -150docker 發布的埠（經 DNAT 後走 forward）：8080、8082、8688從實體網卡進來的，只放行平台主機與 ADMIN_IPS，其餘 drop。非實體網卡（lo、docker bridge）一律 accept
ingest_guard_inputinput，priority -150od-bridge 8500（host network）同上
mgmt_guard_forwardforward，priority -1503000 Grafana、5636 EveBox、8686 Vector API、9443 Portainer只放行 ADMIN_IPS，其餘 drop 並計數
ssh_guard_input（選用）input，priority -15022--ssh-guard 才啟用：只放行 ADMIN_IPS，其餘 drop 並記 log。priority 比自鎖保險的 -100 更早，allowlist 救不了它，鎖到自己只能從主控台救
docker 的 nat / filter 表由 docker 自己管，安裝包刻意只重建 inet secstack 一張表、不 flush 整個 ruleset，否則會打斷所有 port forwarding。重建表會清空 blocklist，所以腳本會先把現有元素（含剩餘 timeout）記下來再補回去。
