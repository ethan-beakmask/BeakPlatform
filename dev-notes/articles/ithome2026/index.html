ITHome2026-WAF 防禦節點運作原理

封包從 Internet 進來之後經過哪些系統、每個系統各管什麼、以及「單獨使用這些開源元件」與「接上 BeakPlatform」之後的處理方式有什麼差別。共六篇，本篇是總覽與閱讀順序。

閱讀順序
  1. 總覽：兩台主機、三條資料流、元件一覽（本篇）
  2. 封包路徑：從 Internet 到被保護網站，逐站說明
  3. 分析系統各管什麼：nftables、WAF、Suricata、CrowdSec、Vector
  4. 事件如何變成案件與決策：Vector → od-bridge → BeakPlatform → 回到防火牆
  5. 系統預設處理 vs 與 BeakPlatform 整合後的處理
  6. 信任邊界與盲區：誰能偽造來源、Suricata 看不到什麼、哪份資料才是全量

一、先建立全景

整套架構只有兩台主機，與安裝章節用同一組位址。主機 A（192.168.0.111）裝 BeakPlatform，是「管制端」：收事件、跑案件流程、記錄決策。主機 B（192.168.0.112）裝 ITHome2026-WAF 安裝包，是「防禦端」：站在被保護網站前面擋攻擊、監聽網路、把事件送出去、再把平台核可的封鎖落地到自己的防火牆。被保護的網站可以是主機 A 上的平台本身，也可以是任何一台內網網站。

三條資料流方向不同，讀後面各篇時請隨時對照：

資料流方向內容圖中線型
請求路徑Internet → 主機 B → 被保護網站使用者或攻擊者的 HTTP 請求與回應。WAF 在這條線上即時放行或阻擋實線
事件路徑主機 B → 主機 AWAF 與 Suricata 的告警，經 Vector 正規化、過濾、封頂後，由 od-bridge 簽章送進平台的事件受理端點藍色虛線
決策路徑主機 A → 主機 B案件簽核產生的封鎖／解封決策。od-bridge 每 5 秒去平台拉取，落地到 nftables、CrowdSec、EDL紅色點線
圖 0-1　兩台主機與三條資料流。事件是「推」上去的，決策是「拉」回來的，主機 B 不需要對主機 A 開任何入站埠。
兩個常被誤會的方向。第一，決策不是平台「推」到防禦端，而是防禦端主動輪詢；所以防禦端不必對外開任何接收埠，平台被入侵也無法直接對防禦端下指令。第二，Suricata 不在請求路徑上，它是旁路監聽，永遠不會擋任何封包；真正即時阻擋的只有 WAF（HTTP 層）與 nftables（IP 層）。

二、元件一覽：誰在哪一層、負責什麼

元件層在請求路徑上？負責什麼產出
Cloudflare（建議的對外入口）邊緣是TLS 終結、DNS 代理、Tunnel 對外入口；依方案另有 DDoS 與受管 WAF 規則。Cloudflare 服務本身是外部服務，但安裝包內含 cloudflared 連接器與 cf_tunnel.py 自動設定，完整支援；不用它也能以內網路徑運作請求標頭 CF-Connecting-IP、Cf-Ipcountry
cloudflared傳輸是從主機 B 主動連出到 Cloudflare 建立 tunnel，把對外 hostname 的流量帶進 docker 網段交給 WAF無
nftablesL3/L4是（最外層）依來源 IP 放行或丟棄：自鎖保險 allowlist、封鎖 blocklist、ingest 面與管理面的來源管制kernel 計數器
WAF：nginx + ModSecurity v3 + OWASP CRSL7 HTTP是（inline）檢查請求與回應內容，異常分數達門檻即回 403；正常請求轉給後端JSON audit log（只記有命中或 4xx/5xx 的交易）
SuricataL3–L7否（旁路）以 Emerging Threats Open 規則比對實體網卡上的封包與應用層協定（HTTP、DNS、TLS）eve.json 告警
CrowdSec行為否依情境（scenario）看時間軸上的重複行為，例如 SSH 暴力破解；LAPI 同時是平台決策的第二份落地點LAPI 決策清單
Vector資料管線否讀 eve.json 與 audit.log，轉成 OCSF 格式，判定攻擊者 IP 可不可信，過濾內網對內網與低嚴重度，分來源與全域封頂兩路輸出：ClickHouse（全量）、od-bridge（篩過）
ClickHouse儲存否一張寬表存全部事件，90 天 TTL；每分鐘彙總視圖供 Grafana可查詢的事件湖
od-bridge（本專案自寫）橋接否把事件加 HMAC 簽章送到平台；用服務帳號拉決策，落地到 nftables、CrowdSec、EDL，回報結果EDL 檔、狀態頁 /stats
BeakPlatform（主機 A）管制否驗簽收事件、路由到案件類型、併案降噪、走簽核流程、寫決策、到期自動解封、保護清單擋誤封案件、決策、稽核紀錄、平台端 EDL
Grafana / EveBox / Portainer（選用）檢視否儀表板、Suricata 告警瀏覽、容器管理。全靠來源 IP 管制，EveBox 與 Vector API 無認證畫面

三、白名單在哪裡

企業對白名單的重視不亞於黑名單：誰永遠不能被封、誰可以連管理介面、誰說的來源 IP 才算數。這套架構的白名單散在八個地方，各管一件事，這裡集中列出，後面各篇提到時會註明是哪一份。

#白名單在哪裡設定管什麼在鏈上的位置
1nftables allowlist（自鎖保險）主機 B .env 的 ADMIN_IPS 與 BEAK_BASE_URL，由 nftables.sh 產生命中者在 input chain 最前面 accept，永遠不會被封鎖決策鎖死。內容是平台主機與管理來源主機 B 最外層，第 1 篇第三節、第 5 篇第三節
2nftables 來源管制（ingest 面、管理面、SSH）同上誰能連 8080／8082／8688／8500，誰能連 Grafana、EveBox、Vector API、Portainer，開 --ssh-guard 時誰能 SSH。不在名單內的連線逾時而不是 403主機 B 最外層，第 1 篇第三節
3Vector 歸因可信來源 TRUSTED_INGRESS_LIST主機 B .env（預設只有 cloudflared 的 172.18.0.250，可用 TRUSTED_INGRESS_EXTRA 加）只有名單內的直連來源送來的 CF-Connecting-IP／XFF 才被採信為攻擊者 IP，其餘「誰打的記誰」Vector 正規化階段，第 5 篇第一節
4EDL 白名單 :8500/edl/allow由平台「放行」決策（action=allow）落地，od-bridge 渲染成 allowlist.txt給外部防火牆抓的允許清單，放在 deny 規則之上；與黑名單同格式、同 TTL 機制決策落地後，第 3 篇第二節
5平台端「封鎖保護清單」平台管理頁「開放防禦 → 封鎖保護清單」（表 od_protected_targets）＋平台 .env 的 OD_PROTECTED_EXTRA_NETWORKS、TRUSTED_PROXY_IPS不得封鎖的網段：出廠 16 條（RFC1918、回送、CGNAT 等）＋企業自訂（辦公室對外 IP、分公司、合作廠商）；另可加「豁免」讓特定內網主機可封。任何流程寫 block 前都會比對，命中即拒寫平台 DecisionWriter 寫入前，第 3 篇第三節、第 5 篇第三節
6API Key 的來源系統白名單平台「安全中心 → API Key」的 scope od_intake.source_systems這把金鑰可以送哪些 source_system 的事件，不在名單內 403平台 intake 驗簽後，第 3 篇第三節
7ClickHouse 帳號層網路白名單主機 B generated/clickhouse-network-allowlist.xml（由 .env 產生）哪些來源能用 secstack 帳號查事件庫：本機、docker 網段、ADMIN_IPS、平台主機事件湖存取，第 2 篇第五節
8WAF 規則放寬（路徑層白名單）主機 B waf/modsec-overrides/modsecurity-override.conf（範例規則 900300，預設註解）對特定路徑移除某些 CRS 規則的檢查目標（例如允許已登入使用者輸入程式碼片段的 API），URL、標頭、cookie 仍照常檢查WAF 請求階段，第 2 篇第二節
兩個容易誤會的：第 1 條只救「直連主機 B 本機程序」的流量，開了 --ssh-guard 又把自己排除在 ADMIN_IPS 外時它救不了 SSH；第 5 條在平台端做一次，防禦端不帶本地副本，所以改了保護清單不必動主機 B。CrowdSec 也有內建 whitelist，出廠只含本機回送位址，本架構沒有另外擴充。

四、一句話版本的運作原理

攻擊進來時，WAF 當場擋掉，這件事不需要平台。平台介入的是「擋掉之後」：把這次攻擊變成一張有人負責、有時限、有紀錄的案件，由人或流程決定要不要進一步封鎖來源 IP，封多久，然後把決定落地到防火牆，到期再自動解除。單獨使用這些開源元件時，前半段一樣會發生，後半段完全不存在。
