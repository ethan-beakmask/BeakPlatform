# 事件路由設定

這一頁用來決定外部資安事件進來後，要被建立成哪一種案件。
一條路由規則代表一種案件類型，例如「WAF 告警」、「弱點掃描發現」或「端點偵測事件」。

## 這頁在做什麼

系統收到事件後，會依優先序從大到小比對路由規則；第一條命中的規則就會被採用，
後面的規則不再比對。命中的規則會指定目標表單，也就是這筆事件要走哪一個處置流程。

如果沒有任何規則命中，事件會被拒絕，API 回應 `422`。這通常代表新來源尚未建立規則，
或事件內容不符合既有條件。

## 路由規則

每條規則包含以下欄位：

| 欄位 | 說明 |
|---|---|
| 名稱 | 管理員辨識用名稱 |
| 格式 | 可限制只套用 `ocsf` 或 `native`；留空表示不限 |
| event_class | OCSF 事件類型；原生格式通常留空 |
| 優先序 | 數字越大越早比對；同分時依建立順序 |
| 目標表單 | 命中後建立的案件表單 |
| 條件 | 事件內容必須符合的比對條件 |
| 聚合 | 是否把重複或持續發生的事件併入既有案件 |
| 啟用 | 停用後不參與比對 |

條件支援 12 個運算子：

| 運算子 | 意思 |
|---|---|
| `eq` | 等於 |
| `ne` | 不等於 |
| `in` | 值在清單內 |
| `not_in` | 值不在清單內 |
| `gt` | 大於 |
| `gte` | 大於等於 |
| `lt` | 小於 |
| `lte` | 小於等於 |
| `contains` | 文字包含 |
| `startswith` | 文字開頭符合 |
| `endswith` | 文字結尾符合 |
| `exists` | 欄位存在或不存在 |

規則條件不支援 regex。需要複雜判斷時，建議讓送件端先把結果整理成明確欄位，
再用上述運算子比對。

## 來源格式（payload profile）

來源格式用來描述原生事件怎麼轉成平台可理解的共同欄位。OCSF 格式已經有固定結構；
原生格式則需要設定欄位路徑。

共同軸線有六欄：

| 軸線 | 說明 |
|---|---|
| `severity_id` | 嚴重度 0 到 6 |
| `actor_ip` | 攻擊者或來源 IP |
| `target_host` | 目標主機 |
| `source_system` | 來源系統 |
| `finding_rule_id` | 偵測規則 ID |
| `occurred_at` | 事件發生時間 |

來源格式也會設定冪等鍵。相同冪等鍵的事件重送時，不會重複建立案件。
如果來源事件有明細陣列，可以設定明細路徑與欄位標籤，案件詳情會用表格呈現。

## 事件聚合

事件聚合用來把同一類持續發生的告警併入同一張案件單，降低重複派案。
未自訂時，規則沿用系統預設：以 `actor_ip` 與 `finding_rule_id` 分組，
視窗 60 分鐘，從案件建立時間起算，低嚴重度事件可併入已結案案件。

聚合設定包含：

| 設定 | 說明 |
|---|---|
| 分組鍵 | 勾選的軸線值全部相同才算同一事件群 |
| 視窗 | 只在指定分鐘數內尋找可合併案件 |
| 起點 | 可從案件建立起算，或從最後一筆事件起算形成滾動視窗 |
| 已結案閾值 | 嚴重度小於等於閾值時，可以只累計到已結案案件；`-1` 表示不併已結案 |

送件端可以提供 `case_group_key`。有提供時，系統會優先使用這個鍵分組，
再套用規則的視窗與已結案設定。這適合「同一掃描任務涵蓋多個 IP」這類送件端最清楚脈絡的情境。

併入既有案件後，系統會累積事件數、最後出現時間、事件摘要、來源 IP 清單，並在嚴重度升高時更新案件嚴重度。
`od_events` 最多保留 200 筆：最早 100 筆與最新 100 筆，中間省略的筆數會另外記錄。

當案件已經由人員簽核完成後，新事件通常會開新單；只有符合已結案閾值的低嚴重度事件才會累積到舊案。
併入事件不會延長 SLA，SLA 仍以案件建立時間計算。

## 試算

「路由試算」可以貼上一包事件 JSON，確認：

- 命中哪一條規則
- 每條規則是否命中，或被哪個條件阻擋
- 命中規則的聚合設定
- OCSF 事件會得到哪一個分組鍵；原生格式則顯示軸線由來源格式決定

試算不會寫入資料，也不會建立案件。

## 常見問題

**改規則會影響既有案件嗎？** 不會。規則只影響之後進來的新事件，不會回溯重算既有案件。

**分組欄位缺值會怎樣？** 只要任一分組欄位缺值，該事件就不會併入既有案件，會各自開案。
這是保守設計，避免把不同事件錯併在一起。

**同軸線但不同來源會互併嗎？** 原生事件會把來源系統納入隔離；OCSF 與原生格式也不互併。
即使軸線值看起來相同，不同來源格式仍會分開處理。

**為什麼沒有 regex？** 規則頁面是給管理員長期維護的設定。regex 容易造成難以預期的命中結果；
建議由送件端先正規化欄位，再用明確運算子比對。
